Does quantization make LLMs faster?

Yes, but for two different reasons. FP8 halves the bytes a model moves and doubles the rate at which a GPU can do the math. Each phase of inference benefits from only one of them.

The idea in one page

Two phases, two bottlenecks, two gains

Quantization reduces the numerical precision of a model's weights and, optionally, its activations, for example from 16-bit BF16 to 8-bit FP8. On hardware with native support, this improves speed in two distinct ways: each value occupies half the bytes, and matrix multiplication runs at twice the peak arithmetic rate.

Which of these gains matters depends on the phase of inference. Every response from an LLM is produced in two phases, and they saturate different parts of the GPU.

The rest of this post derives both effects from first principles, for Qwen2.5-1.5B on an H100: how many FLOPs a forward pass costs, how many bytes it moves, and the prompt length at which compute time overtakes memory time. The analysis is idealized. It assumes kernels reach peak hardware throughput and ignores launch overhead, so read the results as upper bounds rather than measured performance.

Note: attention is treated as multi-head (all projections E × E) rather than Qwen's grouped-query attention, so this post counts 1.65B weights instead of the published 1.54B; the conclusions are unaffected.

FP8 here means W8A8: both weights and activations are stored in the 8-bit E4M3 format (1 sign bit, 4 exponent bits, 3 mantissa bits) in every linear layer, including the tied embedding and output head. The H100's FP8 tensor cores run only when both operands of a multiplication are FP8, so this is the configuration that doubles the arithmetic rate. Attention's scoring and mixing, along with the KV cache, remain in BF16.

computememory The two limits of a GPU

A chef who cooks fast, fed by a conveyor belt that can't keep up

A GPU has two resources that decide how long a forward pass takes. A kitchen is a useful way to picture them.

  • The chef is the tensor cores. The chef cooks at a fixed top speed: the number of floating-point operations (FLOPs) per second the chip can execute.
  • The ingredients are the model's weights and cached values. They sit in a warehouse, the GPU's main memory (HBM), and reach the chef on a conveyor belt with its own top speed: the memory bandwidth, in bytes per second.
  • The workbench is the on-chip memory: registers, shared memory and the L2 cache, about 120 MB in total. The ingredients weigh gigabytes, so they can't stay on the workbench between dishes. They come down the belt every time.

Every forward pass is a dish that needs a certain amount of cooking (FLOPs) and a certain amount of ingredients (bytes). The chef and the belt work at the same time, so the dish is ready when the slower of the two finishes. If the dish needs a lot of cooking per ingredient, the chef is the bottleneck and the pass is compute-bound. If it needs very little, the chef stands idle waiting for the belt and the pass is memory-bound.

Quantization can make the belt deliver fewer bytes. With FP8 arithmetic, it can also make the chef cook faster. Which one helps depends on which one is the bottleneck.
compute Counting the cooking

How many FLOPs does one forward pass cost?

This section walks through Figure 1 from top to bottom. A single sentence is the running example: "The cat sat on the mat because it was tired."

Step 1

From text to numbers

Text is split into tokens, each mapped to an integer ID. The embedding table then gives every token a vector of E numbers. The table has one row per vocabulary token, so it holds V × E weights.

token IDs (S) → look up S rows of Wemb (V×E) → X (S×E)

A row lookup is an indexed read, not a multiplication, so embedding costs zero FLOPs. The result is the activations, a matrix of shape S × E that enters and leaves every layer.

Step 2

The matrix multiply

Almost every purple box multiplies the activations by a weight matrix:

X (S×Ein) × W (Ein×Eout) = Y (S×Eout)

Each of the S × Eout output numbers is a dot product over Ein inputs: one multiplication and one addition per input.

FLOPs = (S × Eout) × 2Ein output numbers × cost of each = 2 × S × Ein × Eout the bold part is the number of weights
Every weight costs 2 FLOPs for every token that passes through it.
Step 3

Query, key and value projections

Attention lets a token gather information from earlier tokens. Resolving what "it" refers to requires looking back as far as "cat". Each token produces a query (what am I looking for?), a key (what do I contain?) and a value (what do I pass on if chosen?).

X (S×E) × WQ (E×E) = Q (S×E) X (S×E) × WK (E×E) = K (S×E) X (S×E) × WV (E×E) = V (S×E)

Weights: 3E². FLOPs: 6SE², at 2 × S × E × E for each of the three matrices. RoPE then rotates q and k by position, which is cheap elementwise work.

Step 4

Attention scores

Each token's query is compared against every token's key. A large score means a strong match, which is how "it" finds "cat".

Q (S×E) × Kᵀ (E×S) = Scores (S×S) Scoring FLOPs = (S × S) × 2E = 2S²E every token pair × cost of one comparison

The grid is S × S: one row for each token asking, one column for each token being asked. In practice a token only looks backwards (causal masking), so about half the grid is skipped; the full grid is counted here for simplicity.

Step 5

Softmax

Softmax turns each row of scores into weights that sum to 1. A row [1.0, 2.1, 2.8] becomes roughly [10%, 30%, 60%], which is how "it" ends up attending mostly to "cat". It costs a handful of FLOPs per score, negligible beside the matrix multiplications.

Step 6

Mixing the values

P (S×S) × V (S×E) = Out (S×E) Mixing FLOPs = (S × E) × 2S = 2S²E output numbers × blending S values each

Scoring and mixing together cost 4S²E. Neither involves learned weights, since both operands are the tokens' own q, k and v. This is real arithmetic for the tensor cores that adds nothing to the weight count, so the two tallies are kept separate.

Step 7

Output projection

One final weight matrix, o_proj, blends the gathered information back into each token's representation. It holds E² weights and costs 2SE² FLOPs.

Step 8

The MLP

After attention, each token is processed separately. The MLP expands each token from E to a larger size H, then shrinks it back.

X (S×E) × Wgate (E×H) = G (S×H) X (S×E) × Wup (E×H) = U (S×H) SiLU(G) ⊙ U = A (S×H) elementwise, cheap A (S×H) × Wdown (H×E) = Y (S×E)

The gate acts as a set of dimmer switches: SiLU maps negative inputs close to 0 and positive inputs close to themselves, and ⊙ scales each entry of U by its switch. Three matrices of E × H give 3EH weights and 6SEH FLOPs.

Step 9

The remaining small pieces

  • RMSNorm rescales each token's vector to a stable size, twice per layer. Its weights and FLOPs are tiny.
  • Residual adds put a block's input back onto its output, so each block makes a small correction. No weights.
  • lm_head turns the final vector into one score per vocabulary token. Qwen2.5-1.5B reuses the embedding table for this, so it adds no weights, but it costs 2EV FLOPs per prediction.

The embedding table and lm_head appear once in the whole model, not once per layer, so they are added on their own rather than multiplied by L.

Step 10

Total weights

Weights per layer = 4E² + 3EH attention + MLP N ≈ VE + L × (4E² + 3EH) embedding + all L layers

Biases and norm gains scale with E rather than E², so they are dropped. To a very good approximation, the model is its embedding table plus the weight matrices in all L layers.

Step 11

Total FLOPs

FLOPs per layer = 8SE² + 6SEH + 4S²E = 2 × S × (4E² + 3EH) + 4S²E 2 FLOPs × tokens × weights attention

The first term is every token through every weight matrix. The second comes from scores and mixing, which multiply activations by other activations, so it has no weights to count against but still costs real FLOPs. Summing over L layers multiplies both terms by L. The lm_head adds 2EV for each of the n tokens we want a prediction for:

FLOPs(S) ≈ 2 × S × L × (4E² + 3EH) + 4 × L × S² × E + 2EV × n weight matrices attention output head
memory Counting the ingredients

How many bytes does one forward pass move?

The standard LLM number format, BF16, uses 2 bytes per number. Writing b for the bytes per weight:

Weight memory = N × b

The KV cache

When the model writes its answer one token at a time, each new token attends to every earlier token's keys and values. Those never change, so they are computed once and saved in the KV cache. Each layer stores one key and one value of E numbers per token:

KV cache per token = 2 × L × E × bkv key and value × layers × numbers each × bytes per number

Prefill writes the cache for every prompt token, and each decode step appends one more.

computememory Which one sets the clock

Compute time, memory time and the ridge point

The tensor cores and the memory system work at the same time, so the time each would need on its own can be worked out separately:

Compute time = FLOPs / F total FLOPs in the pass ÷ peak FLOPs per second
Memory time = Bytes / BW weight and KV cache bytes ÷ memory bandwidth

The actual time is roughly the larger of the two. If compute time is larger, the pass is compute-bound; if memory time is larger, it is memory-bound.

H100 SXMSymbolValue

The ratio of the two rates is the ridge point of the roofline model:

F / BW = 989 / 3.35 ≈ 295 FLOPs per byte

In the time the H100 fetches one byte, it can do about 295 FLOPs. A workload's arithmetic intensity is the FLOPs it performs per byte it moves. Above the ridge point it is compute-bound; below it, memory-bound.

bound by compute Phase 1 · Prefill

512 tokens, one pass. The chef finally has enough to cook.

Prefill processes the entire prompt in a single forward pass and ends when the first output token is produced, so TTFT ≈ prefill time. For the prompt "The cat sat on the", prefill runs every prompt token through the model at once and produces "mat".

Each weight matrix is fetched once and applied to all 512 rows. One delivery from the warehouse supplies 512 dishes. Every weight multiplication is a matrix-by-matrix product (a GEMM), the operation tensor cores are built for.

Activations moving between steps are left out. Most of that traffic is absorbed by the L2 cache and by kernel fusion.

TTFT, in BF16 and FP8

Compute time (1.52 ms) exceeds memory time (1.01 ms), so prefill is compute-bound: the math sets TTFT. With FP8, the weight-matrix FLOPs run at 1,979 trillion per second while attention stays in BF16:

Compute timeFP8 = 1.45 × 10¹² / 1,979 × 10¹² + 0.045 × 10¹² / 989 × 10¹² ≈ 0.78 ms weight matrices, FP8 attention, BF16

The weight bytes halve too, bringing memory time to about 0.52 ms, still below compute. TTFT stays compute-bound at 0.78 ms, roughly half its BF16 value.

Side note · When is prefill compute-bound?

Only when the prompt is long enough. Ignoring the small attention and KV cache terms, compute time exceeds memory time when:

2 × Sp × N / F > N × b / BW ⇔ Sp > F × b / (2 × BW) ≈ 295 tokens

This is the ridge point expressed as a prompt length. W8A8 doubles F and halves b, so the threshold stays at 295 tokens. Weight-only FP8 halves b alone and lowers it to about 148, which is why weight-only quantization helps TTFT only for short prompts.

bound by memory Phase 2 · Decode

One token at a time. Now the belt is the bottleneck.

After the first token, the model generates the rest one token at a time. The duration of each step is the time per output token (TPOT). Each step attends over every token in the cache; with t tokens cached, the average over the whole answer is:

t̄ ≈ Sp + So / 2 = 512 + 64 = 576

TPOT and throughput, in BF16 and FP8

Memory time exceeds compute time by a factor of about 300, so the tensor cores are busy for roughly 0.3% of each step. Decode is memory-bound, and bytes set TPOT. At batch size 1 this doesn't depend on context length: a decode step always does one token's worth of arithmetic per weight fetched.

BF16 TPOT = 1.02 ms → throughput = 1 / TPOT ≈ 983 tokens/s FP8 TPOT = 1.75 × 10⁹ / 3.35 × 10¹² ≈ 0.52 ms → ≈ 1,911 tokens/s weights drop to 1.65 GB; the KV cache stays in BF16 at 0.10 GB

Faster arithmetic is of no use to tensor cores that are already idle, so the whole gain comes from the smaller weights. It falls just short of 2× because the KV cache stayed in BF16.

The whole request

Response time = TTFT + (So − 1) × TPOT BF16 1.52 ms + 127 × 1.02 ms ≈ 131 ms FP8 0.78 ms + 127 × 0.52 ms ≈ 67 ms

There are So − 1 decode steps, since the first output token comes out of prefill.

FP8 (W8A8) roughly halves TTFT and doubles throughput through two unrelated mechanisms: FP8 tensor cores double the arithmetic rate for prefill, and one-byte weights halve the bytes moved in decode. The two gains match because the H100's FP8 peak is exactly twice its BF16 peak, the same factor by which the bytes shrink.

  • Want faster time to first token? Speed up the math: FP8 tensor cores, which need W8A8.
  • Want more tokens per second? Move fewer bytes: smaller weights, which W8A8 and weight-only both deliver.
  • Using weight-only quantization? Expect better throughput, but for prompts longer than about 300 tokens, TTFT barely moves.
